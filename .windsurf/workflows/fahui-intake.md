# 法會專案建立流程

當使用者要建立新的法會報名系統，或希望把既有法會改成另一場法會時，先讀取本流程，再依序執行。

## 1. 先確認是否已有規則檔
優先檢查專案根目錄是否存在以下檔案：
- `fahui-rules.md`
- `fahui-config.json`
- `README.md`
- `.windsurf/workflows/fahui-intake.md`

如果 `fahui-rules.md` 存在，先完整閱讀，再開始修改程式。

## 2. 必問需求清單
如果使用者尚未提供完整規則，必須先詢問以下內容：

### 法會基本資訊
- 法會名稱
- 頁面主標題
- 感謝頁文字
- 是否需要多場法會共用同一套表單

### Ragic 串接資訊
- Ragic 表單網址
- API Key 是否已準備好
- 主表欄位對應
- 子表格欄位對應
- 哪些欄位為唯讀計算欄位
- 哪些欄位必填

### 表單規則
- 基本資料欄位有哪些
- 出生資料欄位有哪些
- 地址資料欄位有哪些
- 公司資料欄位有哪些
- 聯絡資料欄位有哪些
- 哪些欄位顯示/隱藏取決於條件
- 哪些欄位需要條件必填
- 哪些欄位要自動帶入
- 哪些欄位要顯示說明文字

### 子表格規則
- 是否有嬰靈牌位
- 是否有祖先牌位
- 是否還有其他子表格
- 每個子表格的最少/最多筆數
- 每筆子表格的欄位
- 哪些欄位允許空白
- 哪些欄位需要特殊驗證

### 金額規則
- 基本金額
- 加購項目
- 每個加購項目的加價規則
- 金額送到哪個欄位
- 是否要在畫面上顯示金額拆解

### 提交流程
- 送出後是否跳轉感謝頁
- 是否寄送 email
- 是否需要顯示提交成功編號
- 是否需要保留草稿

## 3. 實作原則
- 優先沿用現有 Next.js 專案結構
- 優先修改 `app/page.tsx`、`app/api/submit/route.ts`、`app/layout.tsx`
- 若是新法會沿用舊專案，避免重建整個專案
- 所有欄位變更都要同步檢查前端驗證與後端欄位 mapping
- 子表格變更時，同步檢查 Ragic row ID 格式是否為負數字串
- 若有金額規則，前端顯示與後端提交要同步更新
- 若頁面名稱改變，`layout.tsx` metadata 也要一起改

## 4. 實作後檢查清單
- 表單欄位是否與需求一致
- 條件顯示是否正確
- 必填驗證是否正確
- 子表格資料是否送出成功
- 金額計算是否正確
- 感謝頁是否正確跳轉
- Ragic 欄位 mapping 是否正確
- 是否仍有舊法會名稱殘留

## 5. 每次處理新法會時的回應方式
處理新法會需求前，先明確告知使用者：
- 我會先讀取 `fahui-rules.md` 與本 workflow
- 若規則不足，我會列出缺少的欄位與規則問題
- 規則確認後，再開始改程式
